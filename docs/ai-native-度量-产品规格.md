# AI Native 度量

## 1. 业务目标

负责人要以研发平台产品经理的判断，讲清一件事能不能交给 AI：做成没有、人被打扰几次、背景被补了几次。现在这三件事没有同一套说法。只看用了多少次、写了多少，回答不了它们；单独看一次交付花了多久，也看不出人被打断几次、背景被搬了几次。

本期做两件事。第一，给出一页可以一次讲完的口径，使个人信任账本和团队的 L1、L2、L3 用同一套三条账。第二，在负责人自己的一个真实仓库或博客上，把一条工作读成这三条账。成功状态：阅读者只听这一页，就能复述三条账、取不到时的结果，以及个人样本如何对应到团队三层；样本能够读取时，这一条的三账并列出现，取不到的那一账写明无法判断。对照物是：没有这页口径时，缺失会被当成没发生，个人样本和团队三层会变成两套说法。本期不测量 AI 是否提高了交付效果，也不把作品当作做过真实企业项目的证明。

已确认：取不到的账，结果是 UNKNOWN。它不能写成 0，也不能留空。手册案例里的效果数字没有基线、口径和对照，不作为实施理由，也不作为效果证据。检索后没有证据表明别的产品已经提供这三条账，故不把「竞品均已支持」写成实施理由。

假设：提交记录和发布记录只能支撑「做成没有」的一部分。打扰次数和补背景次数多半不在这些记录里。此假设不是已证实的数据结论。

待确认：样本仓库或博客尚未选定。已掌握、待决、责任人与期限见第 4 节。闭合前不把任何仓库写成已有样本，也不预填三条账的结果。

## 2. 业务结构

### 角色、场景与范围

- 角色：负责人写下口径，并在自己的样本上读取一条归因；阅读作品的人听这一页，并核对这一条结果有没有被讲成效果证明。阅读者不另定一套账。
- 场景：作品需要一次讲清「能不能信」。个人信任账本是最小样本。团队 L1、L2、L3 只用同一套账来说明读法。
- 包含：一页口径；三条账（做成没有、打扰了几次、背景补了几次）；取不到时记为 UNKNOWN；在已确认的个人样本上只跑一条归因；口径中写明这套账如何读到团队 L1、L2、L3。
- 不包含：云端个人 Agent；思维图谱；完整的研发效能度量环境，以及把多系统数据收成团队看板；Agent 身份与权限治理；对任何团队给出 L1、L2、L3 的数字；对他人排名；测量或声称 AI 的交付效果；把作品说成做过的真实企业项目；用外部案例的效果数字充当本条证据；在样本未定时空仓库上预填结果。
- 依赖项（如有）：负责人自己的、已有真实工作记录的仓库或博客，尚未选定。提交记录和发布记录只在它们存在时，作为「做成没有」的部分证据。
- 本期无单独原型。口径是可以一次讲完的说明，不是界面。

### 流程与路径

负责人先核对一页口径：三条账、UNKNOWN、个人信任账本和团队三层必须说成同一套。说不成则不讲述，也不跑归因。说得成之后看样本。样本未确认，则不跑归因，并说明样本未定。样本是空的，或没有可点名的一条工作，则不跑归因，并说明没有可归因的工作。样本已确认且有真实工作，则选定一条工作。完成状态已经写明，才对照它判断做成没有；尚未写明，则不判做成或没做成，这一账为 UNKNOWN，打扰和补背景仍分别取证。每一账证据足够，就写下该证据支持的结果；证据不足，该账记为 UNKNOWN。三账并列。若有人索取团队三层的数字，本期不提供，只保留口径里的读法。讲述必须把口径、这一条结果、本期没有测量的效果分开；混在一起则停住，不得讲成效果或企业项目证明。

  B -->|是| D{样本是否已确认}
  D -->|未确认| E[不跑归因，说明样本未定]

  S --> I{该账证据是否足够}
  H --> I
  I -->|足够| J[写下该证据支持的结果]
  I -->|不足| K[该账记为 UNKNOWN]

  L --> M{是否在索取团队三层的数字}

## 3. 用户故事

1. 作为负责人，在要把个人样本和团队三层讲成同一套判断时，需要一页口径说清三条账以及取不到时的结果，以便阅读者不用第二份定义就能复述。
2. 作为负责人，在自己的一个真实仓库或博客上，需要把一条工作读成三条账，以便得到一份最小的信任账本，并且取不到的账有明确结果。
3. 作为阅读作品的人，在听这一页口径和这一条归因时，需要把口径、这一条样本的结果、尚未测量的效果分开，以便判断的是产品取舍，而不是一份企业效果证明。

## 5. 边界与异常

| 情形 | 业务预期 |
|------|----------|
| 口径还不能一次讲清三条账、UNKNOWN，以及个人与团队三层的关系 | 不讲述，不跑归因，不给出任何账的结果 |
| 样本尚未确认 | 不跑归因，说明样本未定，不给出三条账数字 |
| 样本已确认，但是空的，或没有可点名的一条工作 | 不跑归因，说明没有可归因的工作。不把空写成 0，也不写成 UNKNOWN |
| 该账证据足够 | 写下该证据支持的结果：做成了、没做成，或可点名的次数 |
| 完成状态尚未写明 | 不判做成或没做成。「做成没有」为 UNKNOWN。打扰和补背景仍按各自证据分别给出 |
| 只有提交记录，发布记录也不足以证明完成状态 | 「做成没有」为 UNKNOWN。记录里没有打扰或补背景时，这两账也是 UNKNOWN，不得写成 0 |
| 打扰无法点名到具体次数 | 该账为 UNKNOWN，不写 0，不留空 |
| 补背景无法点名到具体次数 | 该账为 UNKNOWN，不写 0，不留空 |
| 另有证据表明打扰或补背景确实没有发生 | 该账次数为 0 |
| 只有部分账有证据 | 有证据的照实写，没有证据的为 UNKNOWN，不得用有证据的账填补 |
| 要求本期给出团队 L1、L2 或 L3 的数字 | 不提供数字，只保留口径中的读法 |
| 用外部案例的效果数字充当本条证据，或把这一条讲成 AI 交付效果或真实企业项目 | 不采纳这种讲法。口径、这一条结果、未测效果必须分开 |

## 6. 验收标准

1. 负责人出示一页口径后，阅读者能复述：三条账各自在问什么；取不到时结果是 UNKNOWN，不能写成 0，也不能留空；个人信任账本和团队 L1、L2、L3 用的是同一套账；本期只对一条个人归因给出结果；提交记录和发布记录只能支撑「做成没有」的一部分，这是假设。（故事 1、故事 3）
2. 样本已确认，且这一条工作的完成状态已经写明时，负责人给出这一条的三条账。每一账要么是有证据的结果，要么是 UNKNOWN；三账并列，缺证据的账不被另外两账填上。（故事 2）
3. 阅读者能指出：作品没有把这一条归因，或外部案例中的效果数字，说成已测出的 AI 交付效果，也没有把它说成做过的真实企业项目。（故事 3）
4. 第 5 节各情形的业务预期即为该情形的验收。此处不逐条复述。

## 7. 术语表

| 术语 | 在本规格中的含义 | 不包括 | 边界 |
|------|------------------|--------|------|
| 三条账 | 对同一条工作要同时回答的三件事：做成没有、打扰了几次、背景补了几次 | 使用次数；代码行数；另一套团队指标 | 三账并列。某一账的结果不能填补另一账 |
| 做成没有 | 这条工作有没有到达事先写明的完成状态 | 代码已经写完；测试已经通过 | 结果只为做成了、没做成或 UNKNOWN |
| 打扰 | 负责人被 Agent 的通知、确认请求或未结束的等待拉走一次注意力 | Agent 自行完成、人没有中断的过程；人并未中断的通知 | 一次等于负责人能单独点名的一次中断 |
| 补背景 | 负责人为让这件事继续，向 Agent 补上它当时没有的背景 | Agent 自己已经掌握的内容 | 一次等于负责人能单独点名的一次补充 |
| UNKNOWN | 这一账已经要回答，但证据不够，所以无法判断 | 数字 0；空白；没有发起这次度量 | 取不到就必须写下 UNKNOWN。0 只在另有证据表明确实没有发生时使用 |
| 信任账本 | 负责人自己的一条工作上的三条账，是这套口径的最小样本 | 团队汇总；他人排名 | 第一期只跑一条 |
| 一条归因 | 把一条可点名的工作读成三条账 | 多条工作的汇总；空仓库上的预填 | 样本未确认时不存在这条归因 |
| 一页口径 | 一份可以一次讲完的口径说明 | 第二份定义；界面 | 阅读者只凭这一份就能复述第 6 节第 1 条 |
| L1 | 团队范围内，用三条账看 AI 是否进入这件工作的过程 | 使用次数；代码行数；个人排名 | 与信任账本同一套账。本期不出数字 |
| L2 | 团队范围内，用三条账看做成之后质量是否仍有证据 | 没有质量证据时写成质量合格 | 没有质量证据则为 UNKNOWN。本期不出数字 |
| L3 | 团队范围内，用三条账看是否到达事先写明的完成状态 | 只看到产物出现就算交付 | 完成状态未写明则这一问为 UNKNOWN。本期不出数字 |
| 证据 | 负责人能指认、且能对上这一账的记录或事实 | 外部案例的效果数字；另一账的结果 | 指认不到，则该账为 UNKNOWN |
