# PR Review

## 1. 先读什么

1. PR 描述（或 commit message）：这次改动想做什么，会被谁、在什么场景下调用。
2. diff：改了哪些地方。
3. 改动所在文件的相邻代码和仓库规范（README、lint 配置、已有测试），用来判断这次改动是否和周边写法一致。

## 2. 审查原则

按顺序检查。前一条的问题永远比后一条重要。

### 2.1 正确：改动做对了，并且不引入风险

- 代码是否真的做到了 PR 描述说的事。
- 用 PR 描述里的真实调用场景去推输入：取值范围的两端、缺失或为空、格式不合法时会怎样。出错的方式有两种：显式失败，或者静默地给出错误结果。两种都算问题，静默的更危险。
- 来自信任边界之外的输入，被用来访问资源、执行操作或做权限判断之前，有没有校验。
- 测试是否覆盖了上面这些情况。只覆盖正常情况的测试，不能说明改动是对的。

### 2.2 简单优先：可读、可维护

- 能用更少的概念、更少的步骤完成同一件事，就指出来。
- 一个函数做了几件事、嵌套过深、命名看不出用途，都算问题。
- 改动和仓库里已有的写法不一致，又没有理由，算问题。

### 2.3 注释只写代码看不出来的东西

- 注释写「为什么」，不写「是什么」。复述代码的注释算问题。
- 关键决策、约束、不明显的取舍没有注释，算问题。
- 语言或标准库本身的常规行为不需要注释。
- 注释要短。长篇大论的注释算问题。

## 3. 严重程度

每条发现标一个等级：

| 等级 | 含义 | 来自 |
|---|---|---|
| **阻断** | 合入前必须改：会出错、崩溃、返回错误结果，或有安全风险 | 只能来自 2.1 |
| **建议** | 应该改：影响可读性、可维护性，或缺少关键注释 | 2.2、2.3 |
| **nit** | 可改可不改的小问题 | 任意 |

- 2.2、2.3 的问题不能标成阻断。
- 拿不准是建议还是 nit 时，标 nit。
- 没有阻断和建议时，直接说「可以合入」，nit 写在后面即可。

## 4. 输出

先给一句结论：可以合入，或需要先改哪几条阻断。然后按严重程度从高到低列出每条发现：

- **等级**：阻断 / 建议 / nit。
- **位置**：文件和行。
- **问题**：一句话。
- **为什么**：违反了哪条原则，会造成什么后果。
- **建议**：怎么改。

不要为了凑数报问题。
