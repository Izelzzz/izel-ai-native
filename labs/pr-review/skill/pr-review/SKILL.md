# PR Review

## 1. 先读什么

1. PR 描述（或 commit message）：这次改动想做什么。
2. diff：改了哪些地方。
3. 改动所在文件的相邻代码和仓库规范（README、lint 配置、已有测试），用来判断这次改动是否和周边写法一致。

## 2. 审查原则

### 2.1 简单优先：可读、可维护

- 能用更少的概念、更短的路径完成同一件事，就指出来。
- 一个函数做了几件事、嵌套过深、命名看不出用途，都算问题。
- 改动和仓库里已有的写法不一致，又没有理由，算问题。

### 2.2 注释只写代码看不出来的东西

- 注释写「为什么」，不写「是什么」。复述代码的注释算问题。
- 关键决策、约束、不明显的取舍没有注释，算问题。
- 注释要短。长篇大论的注释算问题。

## 3. 输出

每条发现写：

- **位置**：文件和行。
- **问题**：一句话。
- **为什么**：违反了哪条原则，会造成什么后果。
- **建议**：怎么改。

按严重程度从高到低排列。没有发现就直接说没有，不要为了凑数报问题。
